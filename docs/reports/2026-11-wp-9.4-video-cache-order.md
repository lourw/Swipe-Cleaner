# WP-9.4 — Video preloading is race-free (NFR-2, NFR-3)

Date: 2026-11-24. Branch: `nfr-3-video-cache-order`.

## The bug, and whether it was real

`VideoPreloader.preload(id)` (iosMain `VideoItemCache`) launched one detached
coroutine per id and `cancel(id)` removed the map entry and called
`request.cancel()` on the `Deferred` it held. Two callers shared that
`Deferred`: the next deck card's `VideoPlayerView` mounts the player as soon
as the card is on top and awaits `cache.item(id)` — which returned the *same*
`Deferred` the preload coroutine was still filling. The failure shapes:

1. **Cancel tears down an awaited item.** The deck moves fast: `SwipeViewModel`
   calls `cancel(id)` for ids leaving the current + next 3 window, and the
   visible player may have started awaiting the entry at almost the same
   instant. `cancel` cancelled the `Deferred` out from under the awaiting
   player, which saw `CancellationException` instead of the item — the card
   sat on its poster frame with no retry, because the id was no longer in the
   cache and `preload` was never called again for it.
2. **Preload/cancel applied out of order.** `preload` and `cancel` were
   fire-and-forget; nothing serialized them against each other. A `cancel(id)`
   that ran *before* the matching `preload`'s map write lost the race, and the
   preload then inserted an entry for an id outside the window — a warm
   `AVPlayerItem` (plus its in-flight iCloud fetch) that nothing would ever
   evict except a later window pass over the same id, which Shuffle order
   makes unlikely.
3. **No cache bound.** The eviction comment said "bounded by the prefetch
   window" but nothing enforced it; leaks from shape 2 grew the map past four.

**Verdict: the suspected defect was real**, in both the shared-`Deferred`
teardown (shape 1) and the unserialized cancel (shape 2). A regression test
pins each (`NFR-2 cancel does not tear down an item a player is awaiting`,
`NFR-2 cancel that overtakes its preload leaves nothing cached`).

## The fix

**New `WarmItemCache<T>` (`commonMain/dev/swipe/data/`)** — the correctness
core, extracted so it is testable headless against a fake loader:

- **Ordering:** preload/cancel commands are applied by a single consumer
  coroutine over a `Channel` (FIFO by contract), so the state map transitions
  happen in call order. Loads themselves run *concurrently* on the injected io
  dispatcher — a slow iCloud fetch never blocks the next id's fetch — and the
  load's result is re-applied as another in-order command. An entry replaced
  or retired while its load is in flight is marked `stale`; the late result
  cancels the fetch and evicts instead of writing back.
- **Leases:** `item(id)` (the player path) takes a reference-counted lease.
  `cancel`/eviction of a leased entry *retires* it — invisible to new
  `getOrLoad` callers, never counted again — and the in-flight `Deferred` is
  cancelled only when no lease is outstanding. The last release of a retired
  entry cancels its load and frees the slot. A player awaiting an item always
  gets it; eviction waits for the player.
- **Bound:** a hard `maxEntries` — the cache size never exceeds it. Inserting
  beyond the bound evicts the oldest inserted entry (the id furthest behind
  the deck); if that entry is under lease it is *retired* the same way a
  cancelled one is, so the bound holds without ever tearing down an awaited
  item.
- **`null` results are never cached**, so a cancelled or failed id refetches
  on the next preload (matches the R6 retry rule).

**Why not `Dispatchers.Default.limitedParallelism(1)`** (the WP's suggested
mechanism): it confines executions to one thread but **does not preserve
ordering** — the coroutines KDoc says so explicitly ("It is not a mutex!").
Measured on 1.11.0 with a stepping dispatcher: ten sequential `preload` calls
loaded ids `1,2,3,4,6,8,10` with evictions firing between unrelated calls.
The channel actor is the ordered mechanism; `limitedParallelism(1)` remains
only where mutual exclusion (not order) is what's needed.

**`VideoItemCache` (iosMain)** now delegates the player-item path to
`WarmItemCache` with `maxEntries = PREFETCH_WINDOW` (4 =
current + next 3, comment-pinned to `presentation/swipe/PrefetchWindow.WINDOW`). `preload` and
`cancel` return immediately (they enqueue commands; the fire-and-forget API
shape is unchanged). The Live Photo paired-video export path keeps its own
mount-counted map — it already released-then-deleted, so shape 1 could not
occur there.

**`PhotoKitMediaLoader`** image prefetch: `prefetch` / `cancelPrefetch` now
enqueue `PrefetchCommand`s onto a FIFO channel with one consumer coroutine
(the same actor shape as `WarmItemCache`), which runs them on the io
dispatcher — PhotoKit stays off main (§6.8) — and calls
`startCachingImagesForAssets` / `stopCachingImagesForAssets` in **call
order**, so a stop can never land before the start it pairs with and strand a
PhotoKit request that was never registered. `PHImageRequest` cancels
(single-request, owner-cancelled) stay outside the lane — they don't need
ordering, and sharing the lane would let a slow id-fetch block unrelated
cancellations.

## Tests

New `WarmItemCacheTest` (commonTest, fake loader, shared
`StandardTestDispatcher`): 9 tests — 2 `NFR-2 …` (cancel-while-awaited still
delivers the item; every awaiter gets it across a racing cancel) and 7
`NFR-3 …` (cancel-overtakes-preload leaves nothing — the fetch never even
starts; cancel-before-preload is safe; window churn keeps exactly the window;
the bound is never exceeded across a 10-id walk, oldest loads cancelled
first; last-lease release stops a retired load; a warm id is never loaded
twice; a failed load is not cached and retries). All pass; full
`:composeApp:iosSimulatorArm64Test` (553 tests) green;
`scripts/validate.sh --full` green.

The bound tests earned their keep twice over: they surfaced a real
`ConcurrentModificationException` from Kotlin/Native's
`entries.iterator().remove()` in the eviction path (the actor's
`runCatching` was swallowing it, silently dropping entries — every other
survivor set was the fingerprint), and they measured the
`limitedParallelism(1)` ordering failure described above.

## Spec deltas (REQUIREMENTS.md, same change)

- §6.5 step 4: states the ordering guarantee (commands applied in call order;
  an overtaking cancel is a no-op, a losing cancel evicts on arrival), the
  release-before-teardown rule for awaited items, and the hard 4-entry window
  bound on the video cache.
- §6.4 `VideoPreloader` sketch: preload/cancel comments updated to match.
- `docs/coverage.md`: NFR-2 gains its first automated tests (ordering/teardown
  races), NFR-3 gains the video window-bound tests; totals 6 → 7 NFRs with
  automated coverage of the testable core.
