## What was built

A **Hide** button on the swipe `TopBar`, immediately left of the queue
button, that hides the current card in the Photos library — the asset's
`hidden` flag, so it leaves the library grid and stays in the Hidden album.
Hiding is immediate: no in-app confirmation, no queue. It is **not a
decision**: no decision row is written and the FR-21 kept / queued / skipped
numbers never see it — but the deck and the FR-19 progress advance like a
decision would (NFR-7: only after the write succeeds).

### The write door: `MediaHider`

`domain` gains `HideResult { APPLIED, FAILED }`; `data` gains

```kotlin
interface MediaHider { suspend fun setHidden(id: String, hidden: Boolean): HideResult }
```

a sibling to `MediaDeleter`, implemented in iosMain by `PhotoKitMediaHider`:
a `PHPhotoLibrary.performChanges { PHAssetChangeRequest(forAsset:).hidden = … }`
block that resolves the asset by id (nil lookup → `FAILED`, mirroring the
deleter's not-found path) and never reaches `deleteAssets`.

**Resolution of a spec/plan ambiguity.** `plan.md` WP-8.11 loosely described
the write as `MediaLibrary.setHidden`. That would put a write method on the
type every reader holds, breaking the WP-9.1 split that AGENTS.md rule 1
guards. The WP-9.1 precedent (a `MediaDeleter` the readers cannot name) was
followed instead: `MediaHider` is its own interface, `PhotoKitMediaHider`
its own implementation, and §6.4 was amended in the spec commit to document
the door and to state that the hide path is "*never a method added*" to
`MediaDeleter`/`MediaLibrary`.

### Guards (AGENTS.md rule 1 / §8.3)

`scripts/check-rules.sh` now enforces three things around the new door:

1. `MediaHider` may not be named outside its allowlist — `MediaHider.kt`,
   `PhotoKitMediaHider.kt`, `di/IosModule.kt`, `SwipeViewModel.kt`.
   `CommonModule` passes it as `mediaHider = get()` (lowercase, so the
   presentation wiring never spells the type).
2. `performChanges` is permitted only in `PhotoKitMediaLibrary.kt` (the
   delete path) and `PhotoKitMediaHider.kt` — the guard split so a new
   writer cannot appear in any other platform file.
3. Guards 4/4b/5c strip comment lines before matching (same filter the
   `deleteAssets` guard uses), so doc comments may name the APIs they warn
   about.

`DiSmokeTest` gained the graph half: a `CountingMediaHider` is bound over the
real one and every ViewModel resolves through the production Koin graph —
the five readers and the Queue add nothing, `SwipeViewModel` pulls the door
exactly once, and the singleton means no second pull.

### UI

- `TopBar` takes `onHide` + `hideEnabled`; the button is a `CircleIconButton`
  (`visibility_off`, VoiceOver "Hide from library") wrapped with the queue
  button in one trailing `Row` so `SpaceBetween` keeps them adjacent. It is
  not a verdict color (rule 3: `keep`/`delete`/`skip` colors are reserved).
- The card's VoiceOver custom actions are now
  Keep / Delete / Skip / **Hide** / [Undo], pinned by tests.
- Toasts: success "Hidden in Photos" (3 s), failure "Couldn't hide this
  item — try again". Both ride the existing toast machinery.
- **Hide advance has no fly-off** (§5.6): the asset is already hidden in the
  library when the deck moves, so the card leaves with the plain card swap.
- **Hide undo returns the card in place**: fade in with scale
  0.92 → 1.0, 260 ms `FastOutSlowInEasing`
  (`SwipeSpec.RETURN_IN_PLACE_SCALE_FROM`), no side entry. Reduce Motion
  keeps the fade without the scale. Implemented as
  `SwipeCardState.returnInPlace(reduceMotion)` + a `scaleAnim` applied in
  the card's `graphicsLayer` (extracted to a `cardTransform` extension),
  driven by `SwipeEvent.ReturnCardInPlace`.

### Behavior (`SwipeViewModel`)

`SwipeIntent.Hide(id)` mirrors `Decide`'s guards: stale id dropped,
single-flight (`hideInFlight`), ignored while **any** decision write is in
flight, and Undo is held while the hide write runs. On success a
verdict-less `UndoEntry(id, verdict = null, …)` is pushed and the cursor
advances (stale-advance guard identical to `decide()`); no decision row is
written, so FR-21 counts are untouched by construction and progress counts
the hide through the cursor advance. On failure the card stays (NFR-7) and
`HideFailed` shows.

Undo of a hide step bypasses `UndoDecisionUseCase` (there is nothing to
remove from the store) and calls `setHidden(entry.id, false)` — exactly the
asset the entry names. A failed unhide keeps the entry on the stack and
shows the save-failure toast, so the retry is still one tap away.

**FR-22 interplay:** tapping Hide clears a pending favorite-delete confirm
(the card is leaving the deck; the confirm would be stranded), and the
cleared state is stored on the undo entry — a successful undo of the hide
restores the confirm toast together with the card.

**Emission shape.** A decision or hide write now emits exactly two states:
the `deciding`/`hiding` toggle-up at the tap and the settled state carrying
the flag back down (failure toast, `publish`, or `finish`). This is the
same shape FR-32's share loading states use, and it is what lets the Hide
button visibly disable mid-write. Sixteen existing turbine tests were
adapted with an `awaitDecidingToggle()` fixture helper that consumes the
toggle and asserts the card has not moved.

## Hidden assets and the deck (verifier addendum 4)

PhotoKit itself guarantees the deck never shows a hidden asset: every fetch
in `PhotoKitMediaLibrary` uses `PHFetchOptions`, and
`PHFetchOptions.includeHiddenAssets` **defaults to `false`** — it is set
nowhere in the codebase (grep-verified; the only mention is a comment in the
fake). So a hidden asset drops out of `fetchAssetIds`/`items` on the next
deck build, and FR-6's unresolved-id tolerance covers a mid-session hide
racing a page fetch. `FakeMediaLibrary` mirrors the guarantee:
`hiddenAssetIds` is excluded from **every** read path, and
`SwipeViewModelHideTest` proves at BuildDeck level that a hidden asset is
absent from a freshly built deck.

## 👤 Checkpoint for the human

**System prompt on first hide.** `PHPhotoLibrary.performChanges` on a hidden
flag with limited library access *can* surface a system permission prompt
("Swipe Cleaner is trying to hide an item") on a real device depending on
the granted photo permission level. The simulator's authorized state does
not exercise this. Worth one on-device tap of Hide with each permission
level (Limited / Full) before shipping.
