## What was built

The FR-22 favorite-delete confirmation is no longer a toast. It is now
`FavoriteConfirmCard`, bottom-anchored on the deck stage directly above the
action bar — the deck toast's own anchor — so the photo being confirmed stays
fully visible and never resizes. It states the question, offers **Cancel** /
**Delete**, stays until the user acts, an Undo closes it, or the deck moves
on, and nothing pre-selects or auto-accepts anything (NFR-5). A fresh drag on
the pending card while it is up cancels the confirmation (U3).

## Component: `FavoriteConfirmCard` (all `SwipeTheme` tokens)

`composeApp/src/commonMain/kotlin/dev/swipe/ui/components/FavoriteConfirmCard.kt`

- **Card**: `fillMaxWidth`, `surfaceRaised` on `radii.sheet`, `spacing.m`
  padding, `spacing.xxs` between text lines; title + supporting line + button
  row, all centered.
- **Title** "Delete this favorite?" — `typography.headline`, `textPrimary`.
- **Supporting line** "Queues it with the items waiting to be deleted." —
  `typography.callout`, `textSecondary`.
- **Buttons**: iOS alert convention, side by side, `weight(1f)` each — equal
  size — every cell `heightIn(min = sizes.minTouchTarget)` (44 dp, §5.5).
  **Cancel** left in `accent` (secondary text style) → `onCancel`; **Delete**
  right in `delete` (the only element in the verdict color) → `onDelete`. A
  `border`-colored hairline sits between them, drawn inside the Delete cell
  via `drawBehind` so it takes no layout width and both cells measure exactly
  equal (a flow-Box divider measured 495 vs 496 px in tests).
- **Nothing pre-selected / no timers (NFR-5)**: the component has no
  auto-dismiss of any kind; the DELETE is written only through `onDelete`.
- **Entrance**: 150 ms fade (`FAVORITE_CONFIRM_ENTRANCE_MS`) through an
  `Animatable`, published to tests via `FavoriteConfirmAlphaSemanticsPropertyKey`
  (mirrors the `RotationZ` hook). `reduceMotion = true` starts at alpha 1 with
  no animation.
- **NFR-8**: container is a `LiveRegionMode.Assertive` region whose
  `contentDescription` is the title, so VoiceOver announces the question as
  the card appears; buttons read "Cancel, keep this photo" / "Delete favorite"
  with `Role.Button`.

## Wiring (`SwipeScreen.kt`)

`DeckToastOverlay` renders the card when `toast == FavoriteConfirm &&
pendingFavoriteDelete != null` at `Alignment.BottomCenter` +
`toastHostPlacement(clearHomeIndicator = false)` — the same anchor the toast
uses — and every other message (and the defensive pending-null case) stays on
`ToastHost`. Cancel sends `SwipeIntent.DismissToast` (records nothing);
Delete sends `SwipeIntent.ConfirmFavoriteDelete(pending)` (FR-13: names the
card). `toastSpec()` was deleted from SwipeScreen; the confirm-style
`ToastSpec` fields stay for `ToastHost`'s own fuse semantics.

**ViewModel unchanged** — the existing guards already satisfy the spec:
`decide()` re-asks on a favorite DELETE, `ConfirmFavoriteDelete` clears the
pending id synchronously before recording, and `publish()` clears the pending
confirm on any deck move, which is how an Undo (or any navigation) closes the
card.

## U3 gesture gating

- `SwipeCard` gained an optional `onDragStart: () -> Unit`, fired inside
  `swipeDragGestures.onDragStart` **only for live drags** (not programmatic
  settles). It is threaded as `State<() -> Unit>` through
  `rememberUpdatedState` into `swipeDragPointerInput`, because `pointerInput`
  captures its arguments once at launch.
- `CardStack` (`DeckMotion.kt`) passes it through (default `{}`), so the
  other `SwipeCard` callers are untouched.
- `DeckStage` wires it to: if `state.pendingFavoriteDelete != null` →
  `onIntent(SwipeIntent.DismissToast)`. Moving the finger over the pending
  card cancels the confirmation exactly like **Cancel**; the card remains for
  a fresh verdict, and a swipe completed after the cancel is an ordinary
  KEEP/SKIP/DELETE through the normal commit path — never a DELETE for the
  pending favorite without the confirm.

Pinned by (deck-level, real pointer input):
- *U3 starting a drag while the confirm is up cancels it without deciding* —
  a short drag dispatches exactly `[DismissToast]`, no `Decide`, card stays.
- *U3 a right swipe over the confirm cancels it and keeps the card* —
  dispatches `[DismissToast, Decide(KEEP)]` in order: cancel first, then an
  ordinary verdict.

## Deviations (documented)

- **No forced VoiceOver focus** on appear — CMP 1.12.2 has no cross-platform
  focus-move API; the Assertive live region + container description carry the
  announcement instead (same pattern as `Toast`).
- **Confirm UI tests live in a new class** (`SwipeScreenFavoriteConfirmTest`)
  to keep `SwipeScreenTest` under detekt's LargeClass limit (551 lines after
  removing the two toast tests).
- **Pending-null fallback**: if `toast == FavoriteConfirm` ever arrives with
  no pending id, the deck shows the old plain-toast copy rather than a card
  with nothing to confirm (state-machine defense, tested).
- The gallery (`DebugComponentGallery`) swapped its stale confirm-toast
  example for the card.
