## What was built

While the in-app delete confirmation is up, it now shows what the queue would
free — best-effort, and never in the delete's way:

1. **`StorageEstimate` (domain/model).** A sealed three-state result —
   `Complete(totalBytes)`, `Partial(totalBytes)` (a lower bound: some assets
   unreadable), `Unavailable` — so "we don't know" is a fact the UI can
   render honestly instead of a zero or a lie. Empty id list → `Complete(0)`.

2. **`MediaSizing` (data/).** `suspend fun estimateBytes(ids): StorageEstimate`
   — a read-only door sitting beside `MediaSharer`/`MediaHider`. It gains no
   delete power (hard rule 1 untouched: `MediaDeleter` stays confined to
   `CommitDeletionsUseCase`), so no check-rules guard change was needed.
   Koin-bound in `IosModule` as `PhotoKitMediaSizing`.

3. **`PhotoKitMediaSizing` (iosMain/platform).** Per id: the shared
   burst-inclusive `assetById` fetch, then `PHAssetResource.assetResourcesForAsset`
   and the KVC read `valueForKey("fileSize")` → `NSNumber.longLongValue`.
   A nil answer, a throw (KVC raises `NSUnknownKeyException` if Apple ever
   drops the key — caught per resource), or a 0 answer makes that asset
   unreadable; some unreadable → `Partial`, none readable → `Unavailable`.
   Only resource *metadata* is read — no data request, so nothing downloads
   (NFR-6). The whole sum runs on `Dispatchers.Default`.

4. **`QueueViewModel` sizing side-channel.** `QueueUiState` gained
   `deleteSize: StorageEstimate?` (null = loading or omitted). `RequestDelete`
   opens the dialog synchronously and fires a fire-and-forget sizing job over
   the queue snapshot; `CancelConfirm`/`Close`/`ConfirmDelete` cancel the job
   so a late result can never decorate a later dialog, and a throw is
   swallowed as `Unavailable` — sizing never surfaces as an event or error.
   `confirmDelete` never consults sizing: the FR-25 token construction is
   byte-for-byte what it was before.

5. **The honest line.** `ConfirmDialog` gained an optional `secondaryMessage`
   (same `callout` `textSecondary` style, §5.8) and `QueueScreen` passes
   `deleteSizeLabel(state.deleteSize)`:
   "About 1.2 GB. Space is freed after Recently Deleted clears."
   ("**At least** …" when some sizes could not be read; nothing at all when
   `Unavailable`, still loading, or zero.) The unchanged "They'll move to
   Recently Deleted for 30 days." message stays the dialog's own message, so
   the confirmation is fully usable without the new line (R3).

6. **Byte formatting.** `formatStorageBytes` (in `StorageFormatting.kt`,
   beside the label so both are testable without Compose): decimal
   1000-based units the way iOS labels storage, one decimal below 10 units
   and none above — "9.5 MB", "850 MB", "1.2 GB", "25 GB" — with tenth-place
   rounding that carries units, so it never reads "1000 MB".

## Notes / deferrals

- **Estimate scope is the queue as it stood when the dialog opened** — an
  "About" number, not a receipt (spec'd).
- **iCloud-only originals may free no device space at all** — the "About"
  hedge covers it; no separate iCloud-only wording (kept simple per §5.8).
- **No caching / no batching of size reads**: the queue dialog is one-shot
  and `PHAssetResource` metadata reads are cheap; measured batching would be
  speculative.
- `check-rules.sh`: the safe-area guard's allowlist gained `StorageFormatting.kt`
  (a pure formatting file under `ui/screens/`, not UI at all — same precedent
  as `CommitLatencyTrace.kt`). No other production file touches the new types;
  the `MediaDeleter` guard passes untouched.
- Hard rules honored: no hex/dp/sp outside theme, existing tokens only, no
  network, no `MediaDeleter` exposure, decisions still persist-before-advance
  (untouched path), PhotoKit work off the main actor.
