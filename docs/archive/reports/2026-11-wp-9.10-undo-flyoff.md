# WP-9.10 — Undo during the fly-off window is queued, not dropped (FR-15, §5.6)

Date: 2026-11-24. Branch: `fr-15-undo-flyoff`.

## The gap, and whether it was real

FR-15 (WP-7.2 shape): while a decision write is in flight, an Undo tap was
**ignored** — "the deck never rewinds under a completing write." But the tap
does not arrive at the ViewModel when the user presses the button: the Decide
intent only goes out when the card's **fly-off animation ends** (§5.6), so
"while a write is in flight" was only the tail of the window. The full user
window is the whole ~220 ms flight plus the write:

1. **Gesture path.** Release past the threshold → 220 ms flight → Decide →
   write → advance. An Undo tapped anywhere in the flight was dropped twice
   over: mid-flight the card is committed but the ViewModel has no write yet,
   and the Undo affordance fired `SwipeIntent.Undo` against whatever the
   *previous* stack top was — or, with `canUndo = false`, did nothing visible
   at all.
2. **Button path.** Nudge (80 ms) + fly-off + Decide + write: same swallow,
   with a wider window.

**Verdict: real.** The tap belongs to the swipe in flight, and silently
losing it is exactly what FR-15 must not do. The fix was a product decision
(queued vs dropped at release): **queued** was chosen — the Undo fires once
the commit lands and the card comes back, as if the tap had arrived after the
animation.

## The fix

Two halves, one per window segment:

**UI hold (`rememberUndoFlyOffHold`, `SwipeScreen.kt`).** The deck's single
Undo affordance (ActionBar and the card's custom action both take it) holds
the tap only while a flight that has not yet dispatched its Decide owns the
card — `cardState.committedVerdict != null` and the card's `flightToken`
(the count of fly-offs started, bumped at both flight-start sites in
`SwipeCardState`/`SwipeCard`) differs from the token of the flight whose
Decide went out. One slot; extra taps are
ignored, mirroring the removal single-flight. When the flight ends, the
wrapped `commit` records the token, sends the Decide, and the held Undo rides
immediately behind it — so the ViewModel always sees `Decide(id)` then
`Undo`, and the tap is attributed to the flight it was made against, never an
older step. The window is **release → dispatch**: taps made after the Decide
goes out reach the ViewModel directly, where the queue below owns the write
window; a returned card (refused favorite, failed write) is the same id, and
its retry's flight re-arms the hold. This per-flight scoping is what keeps a
held tap from surviving an aborted flight and rewinding a later decision
(verifier findings, round 1).

**ViewModel queue (`pendingUndo`, `SwipeViewModel.kt`).** `takeUndoStep()`
(now the guard pass of `undo()`) queues the tap when `decideInFlight` is
non-empty instead of dropping it. The completing `commitDecision` fires it
**after the advance**, so it rewinds exactly this decision and the card comes
back with the normal Undo-return animation. Three terminal cases clear the
slot without firing: the write **failed** (NFR-7 — the revert is already
bringing the card back, there is nothing to undo), the **stale-advance race**
loser (the deck moved under the tap; rewinding would rewind the wrong card),
and `finish()` (a finished run clears the stack, so the fired Undo would be a
no-op against the empty stack anyway). A hide write still **drops** Undo
outright (FR-38): a hidden card has no fly-off to return from.

The rewrite also extracted `commitDecision` (the write-and-advance half of
`decide`) so the queue logic lands without tripping detekt's complexity
limits — behavior-preserving.

## Tests

`SwipeViewModelUndoTest` (replaces WP-7.2's two drop tests with queue
semantics): queued Undo fires after the advance; a failed write discards it;
only one Undo is queued (second tap ignored); hide-write tap still dropped.
`SwipeScreenUndoFlyOffTest` (new file, keeps `SwipeScreenTest` under
LargeClass) pins both UI paths frame-by-frame: mid-flight the tap sends
nothing; when the flight ends the intents arrive as `Decide` then `Undo`,
in that order, for the gesture and the button path. The round-2 regression
pins: a tap after the Decide goes out is sent straight through (the VM
queue's window); a held tap cannot leak into the next card's commit; and the
hold re-arms when the same card flies off again after a ReturnCard return.

604 tests, 0 failures. `scripts/validate.sh --full`: see the tracker.

## Deliberate non-goals

- No new UI→VM protocol: the gate emits an ordinary `SwipeIntent.Undo`
  (§6.6 — transient animation state stays in the composable).
- No multi-slot queue: one Undo per flight, matching the existing
  single-flight semantics.
- The hide path keeps WP-7.2 drop behavior (documented in the FR-15 spec
  edit).

## 👤 Device-check candidates

- Swipe a card and tap **Undo mid-flight** (before it leaves the screen):
  the card flies off, then flies straight back with the normal Undo-return
  animation; the card *before* it is untouched. Same for the button path
  (Keep/Delete/Skip nudge + flight).
- **First card of a session** (empty stack): swipe + mid-flight Undo → the
  card comes back; a mid-flight Undo with nothing in flight behind it (a
  no-decision tap) stays a no-op.
- **Double Undo mid-flight**: exactly one rewind, not two.
- **Last card of the deck**: swipe + mid-flight Undo while the summary
  loads — the run finishes and the queued Undo is a no-op (nothing to undo
  past the summary).
- **VoiceOver**: the card's Undo custom action mid-flight behaves like the
  button (it rides the same gate).
- Known unchanged edge (no regression, worth an eye): favorite refused
  (FR-22) + mid-flight Undo — the favorite comes back with the confirm and
  the *previous* step is undone, as before this WP.
